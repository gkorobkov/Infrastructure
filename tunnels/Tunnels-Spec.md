# Техническое задание: автоматизация HTTPS-туннелей для локальных webhook

## 1. Цель

Реализовать три независимых PowerShell-скрипта для создания публичных HTTPS-туннелей к локальному HTTP-серверу пользователя:

1. Cloudflare Quick Tunnel
2. ngrok
3. localtunnel

Пользователь запускает один скрипт, который самостоятельно выполняет предварительные проверки, помогает установить зависимости, запускает туннель и выводит готовый публичный HTTPS URL для использования в Web UI.

Скрипты предназначены для учебных и демонстрационных проектов с n8n, Python/FastAPI, Node.js и другими локальными HTTP-серверами.

Основной сценарий (Web UI может находиться на любом внешнем HTTPS-адресе; запросы также могут отправлять другие внешние клиенты):

```text
Web UI:
https://service-name.ru

         |
         | HTTPS POST
         v

Публичный туннель:
https://<generated-hostname>/webhook/my-agent

         |
         | Forwarding
         v

Локальный сервер:
http://127.0.0.1:5678/webhook/my-agent
```

В документации и сообщениях интерфейса использовать слово «пользователь». Не использовать слово «студент».

5. Не изменять существующую бизнес-логику.
6. Не перезаписывать пользовательские конфигурации.
7. Не добавлять новые зависимости проекта, если можно обойтись средствами PowerShell.


## 3. Поддерживаемые платформы

Основная платформа:

- Windows 10/11
- Windows PowerShell 5.1
- PowerShell 7

Скрипты должны запускаться без Docker и WSL.

Приоритет — отсутствие необходимости запускать PowerShell от администратора.

Если установка инструмента требует административных прав, объяснить причину и предложить альтернативную установку в пользовательскую директорию.

Не изменять глобальную Execution Policy.

В README объяснить безопасный запуск:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\start-cloudflare.ps1
```

Объяснить, что эта команда применяет политику только к новому процессу PowerShell. Пользователь должен предварительно проверить источник скрипта.

## 4. Общий контракт скриптов

Реализовать следующие параметры:

```powershell
param(
    [ValidateRange(1, 65535)]
    [int]$Port = 5678,

    [string]$WebhookPath = "/webhook/my-agent",

    [string]$LocalHost = "127.0.0.1",

    [switch]$InstallIfMissing,

    [switch]$SkipPublicCheck,

    [switch]$VerboseOutput
)
```

Дополнительные параметры конкретных провайдеров допускаются.

Входные значения валидировать до выполнения действий.

WebhookPath:

- Должен начинаться с `/`.
- Может содержать query string.
- Не должен содержать CR/LF или управляющие символы.
- Не должен интерпретироваться как команда.
- Должен корректно объединяться с публичным URL.
- Не должен приводить к двойным `/`.
- По умолчанию `/webhook/my-agent`.

LocalHost:

- По умолчанию `127.0.0.1`.
- Принимать только допустимые локальные адреса или явно разрешённые локальные hostname.
- Не допускать произвольной публикации внешних серверов без осознанного указания пользователя.

## 5. Общий алгоритм запуска

### Шаг 1. Приветствие

Вывести:

```text
========================================
 HTTPS Tunnel Setup
 Provider: Cloudflare
========================================

Локальный сервер: http://127.0.0.1:5678
Webhook path: /webhook/my-agent

Проверяю окружение...
```

Название провайдера подставлять автоматически.

### Шаг 2. Проверка окружения

Проверить:

- ОС и версию PowerShell.
- Наличие интернет-соединения, насколько это возможно.
- Доступность необходимых команд.
- Наличие локального HTTP-сервера.
- Доступность порта.

Использовать короткие таймауты.

Не считать отсутствие ответа от произвольного внешнего сайта доказательством отсутствия интернета.

### Шаг 3. Проверка локального сервера

Проверить TCP-подключение к заданному адресу и порту.

Затем выполнить безопасный HTTP-запрос к корню сервера или другому явно указанному health endpoint.

Важно:

- HTTP 401/403/404 не означает, что сервер недоступен.
- Не выполнять POST на webhook без согласия пользователя.
- Не считать любой открытый TCP-порт гарантией корректной работы webhook.
- Не запускать автоматически n8n, Python или Node.js сервер.

Если сервер не найден:

```text
[ERROR] Локальный сервер недоступен.

Проверен адрес:
http://127.0.0.1:5678

Туннель перенаправляет запросы на локальный
сервер, поэтому сначала его нужно запустить.

Что можно сделать:
1. Запустить n8n или другое приложение.
2. Проверить номер порта.
3. Повторить запуск скрипта.
```

Завершить работу с ненулевым exit code.

### Шаг 4. Проверка клиента туннеля

Проверить наличие исполняемого файла.

Если клиент найден, вывести версию.

Если отсутствует, предложить:

```text
Cloudflare Tunnel не установлен.

Можно установить его автоматически.

Установить сейчас? [Y/N]
```

Если указан `-InstallIfMissing`, выполнять установку без дополнительного вопроса, поскольку пользователь уже явно разрешил её параметром.

Использовать только официальные источники.

Предпочитать поддерживаемые менеджеры пакетов, например winget, с проверкой результата установки.

Если менеджер пакетов недоступен, предложить установку официального бинарного файла в пользовательскую директорию.

Проверять архитектуру ОС, результат скачивания, подлинность или контрольную сумму там, где доступны официальные средства проверки.

Не загружать исполняемые файлы с неофициальных зеркал.

После установки повторно проверить доступность клиента.

### Шаг 5. Запуск

Запустить клиент туннеля.

Требования:

- Не блокировать чтение stdout/stderr.
- Не допускать deadlock при большом выводе.
- Поддерживать таймаут ожидания публичного URL.
- Отслеживать завершение дочернего процесса.
- Корректно обрабатывать Ctrl+C.
- Не оставлять осиротевшие процессы.
- Не завершать чужие процессы туннелей.
- Не запускать дублирующий туннель без предупреждения.

Если URL не получен, показать диагностическое сообщение и безопасно завершить дочерний процесс.

### Шаг 6. Получение публичного URL

Получить URL из официально поддерживаемого API, вывода CLI или другого документированного механизма.

Не предполагать, что URL всегда появляется в одной и той же строке.

Проверить:

- Схема `https://`.
- Наличие допустимого hostname.
- Отсутствие управляющих символов.
- Отсутствие случайно захваченного текста из логов.

Сформировать:

```text
Public URL:
https://example.trycloudflare.com

Webhook URL:
https://example.trycloudflare.com/webhook/my-agent
```

Не использовать примерный URL как фактически полученный.

### Шаг 7. Проверка публичного адреса

Проверять публичный URL только безопасными запросами.

Не выполнять POST на рабочий webhook автоматически.

Проверять DNS, TLS и доступность HTTP endpoint, насколько позволяет провайдер.

Различать:

- Туннель создан.
- Публичный URL получен.
- HTTPS endpoint доступен.
- Запрос достиг локального сервера.
- Webhook успешно обработал POST.

Последний пункт нельзя объявлять успешным без реального функционального теста.

Если нет выделенного health endpoint, явно сообщить, что полная проверка webhook не выполнена.

Если проверка публичного адреса не удалась, не уничтожать работающее соединение автоматически: показать предупреждение и варианты диагностики.

### Шаг 8. Финальный вывод

```text
========================================
 TUNNEL READY
========================================

Provider: Cloudflare

Local server:
http://127.0.0.1:5678

Public URL:
https://example.trycloudflare.com

WEBHOOK URL:
https://example.trycloudflare.com/webhook/my-agent

Скопируйте WEBHOOK URL в Web UI.

Статус:
- Локальный сервер: доступен
- Туннель: подключён
- HTTPS URL: получен
- Проверка webhook POST: не выполнялась

Туннель работает, пока запущен скрипт.

Для остановки нажмите Ctrl+C.
========================================
```

Реальные статусы должны соответствовать выполненным проверкам.

Опционально предложить скопировать URL в буфер обмена с использованием `Set-Clipboard`, если команда доступна.

Не сохранять автоматически URL в файлы проекта.

## 6. Скрипт start-cloudflare.ps1

Использовать Cloudflare Quick Tunnel.

Основная команда:

```powershell
cloudflared tunnel --url http://127.0.0.1:5678
```

Требования:

1. Проверить наличие `cloudflared`.
2. При отсутствии предложить установку.
3. Проверить версию.
4. Проверить локальный сервер.
5. Проверить существующую конфигурацию cloudflared на предмет возможных конфликтов с Quick Tunnel.
6. Не удалять и не переименовывать пользовательскую конфигурацию автоматически.
7. Запустить Quick Tunnel.
8. Получить публичный адрес `*.trycloudflare.com`.
9. Проверить HTTPS.
10. Вывести полный webhook URL.
11. Оставить туннель работающим.

Не требовать аккаунт Cloudflare.

Предупредить:

- URL временный.
- При перезапуске URL может измениться.
- Quick Tunnel предназначен для разработки и тестирования.
- Нет гарантии доступности.
- Не поддерживаются SSE.
- Есть ограничения на количество одновременных запросов.

Если Quick Tunnel не запускается из-за существующего config.yaml, предложить безопасное решение, не изменяя пользовательские файлы без подтверждения.

## 7. Скрипт start-ngrok.ps1

Основная команда:

```powershell
ngrok http 5678
```

Требования:

1. Проверить наличие ngrok.
2. При необходимости предложить установку.
3. Проверить версию.
4. Проверить конфигурацию и наличие авторизации.
5. Если авторизация отсутствует, объяснить регистрацию.
6. Предоставить ссылку на получение authtoken:
   https://dashboard.ngrok.com/get-started/your-authtoken
7. Предложить пользователю самостоятельно настроить токен.
8. Использовать официальную команду:

```powershell
ngrok config add-authtoken <TOKEN>
```

В реализации избегать раскрытия токена в истории команд, логах и выводе процесса, насколько это позволяет выбранный способ настройки.

Предпочитать безопасный интерактивный ввод или официальные механизмы конфигурации.

Не запрашивать API key вместо authtoken.

Не хранить токен в репозитории.

После настройки:

1. Запустить ngrok.
2. Получить публичный URL через локальный API ngrok, если доступен.
3. Не считать, что локальный API обязательно работает на стандартном порту.
4. Проверить корректность URL.
5. Вывести полный webhook URL.
6. Сохранить работающий процесс до остановки пользователем.

Если лимит аккаунта исчерпан, показать сообщение об ограничении и предложить альтернативные скрипты.

Не пытаться обходить лимиты ngrok.

## 8. Скрипт start-localtunnel.ps1

Основная команда:

```powershell
npx --yes localtunnel --port 5678
```

Требования:

1. Проверить наличие Node.js.
2. Проверить наличие npm и npx.
3. Если Node.js отсутствует, предложить установку официальной LTS-версии.
4. Не устанавливать Node.js без согласия.
5. Проверить доступность npm registry.
6. Запустить localtunnel.
7. Получить публичный HTTPS URL.
8. Сформировать полный webhook URL.
9. Проверить доступность, насколько возможно.

При первом запуске объяснить, что npx может скачивать пакет из npm.

Не требовать глобальную установку localtunnel.

Если `npx --yes` не поддерживается установленной версией npm, диагностировать проблему и предложить поддерживаемый способ запуска.

Особое внимание уделить возможной странице подтверждения доступа (tunnel password / reminder page).

Если публичный URL открывает страницу подтверждения вместо webhook:

- Не объявлять webhook работоспособным.
- Объяснить проблему.
- Не пытаться обходить защиту автоматически.
- Предложить Cloudflare Tunnel или ngrok.

Предупредить, что localtunnel может быть менее предсказуем для автоматических API/webhook-запросов.

## 10. Интеграция с n8n

Отдельно объяснить два режима n8n.

### Test webhook

```text
/webhook-test/<path>
```

Он доступен только когда тестовый webhook активирован в n8n.

### Production webhook

```text
/webhook/<path>
```

Он требует опубликованного/активного workflow в соответствии с используемой версией n8n.

Пользователь должен самостоятельно указать правильный путь.

Скрипт не должен автоматически менять конфигурацию n8n.

Объяснить, что внешний WEBHOOK_URL в n8n может потребоваться для корректного формирования отображаемых webhook URL, но для ручного обращения по публичному адресу туннеля его настройка не всегда обязательна.

Не менять WEBHOOK_URL автоматически.

## 11. Интеграция с Web UI

Web UI не привязан к конкретному сайту. Обозначать адрес условно:

```text
Web UI https://service-name.ru
```

Пользователь должен:

1. Запустить локальный HTTP-сервер.
2. Запустить один из трёх скриптов.
3. Дождаться публичного HTTPS URL.
4. Скопировать полный webhook URL.
5. Открыть Web UI.
6. Указать URL в настройках webhook.
7. Отправить тестовый запрос.
8. Проверить ответ.

Объяснить, что браузер может требовать корректный CORS даже при использовании HTTPS-туннеля.

Туннель сам по себе не добавляет необходимые CORS-заголовки к ответам приложения.

Если используется n8n, проверить CORS и обработку OPTIONS отдельно.

Не утверждать, что создание туннеля автоматически решает все проблемы CORS.

## 12. Логирование

Сообщения скриптов должны быть на русском языке.

Уровни:

```text
[INFO]
[CHECK]
[OK]
[WARN]
[ERROR]
```

Пример:

```text
[CHECK] Проверяю локальный сервер...
[OK] Сервер доступен.
[CHECK] Проверяю Cloudflare Tunnel...
[WARN] Клиент не установлен.
[INFO] Предлагаю автоматическую установку.
[OK] Клиент установлен.
[INFO] Запускаю HTTPS-туннель...
[OK] Публичный URL получен.
```

При ошибках выводить конкретное действие для исправления.

Не печатать секреты.

Для подробной диагностики использовать `-VerboseOutput`.

## 13. Обработка ошибок

Предусмотреть:

- Отсутствие интернета.
- Недоступность DNS.
- Ошибки TLS.
- Ошибки установки.
- Отказ пользователя от установки.
- Отсутствие авторизации.
- Неверный токен.
- Недоступный локальный сервер.
- Занятый порт служебного API.
- Преждевременное завершение туннеля.
- Невозможность получить публичный URL.
- Некорректный URL.
- Таймаут.
- Прерывание Ctrl+C.

Не использовать бесконечные циклы ожидания без таймаутов.

После запуска туннеля скрипт должен работать до остановки пользователем или завершения процесса клиента.

## 14. Тестирование

Создать Pester-тесты, если Pester доступен.

Тесты должны проверять:

1. Валидацию параметров.
2. Проверку порта.
3. Проверку локального HTTP-сервера.
4. Обнаружение отсутствующих команд.
5. Обработку отказа от установки.
6. Парсинг публичных URL.
7. Формирование полного webhook URL.
8. Обработку query string.
9. Обработку ошибок провайдера.
10. Таймаут ожидания URL.
11. Корректное завершение дочернего процесса.
12. Отсутствие секретов в логах.

Использовать mock-объекты для внешних процессов и сетевых вызовов.

Не требовать реальных аккаунтов ngrok для автоматических unit-тестов.

Не выполнять реальную установку программ в unit-тестах.

Дополнительно реализовать или описать ручной smoke test:

```text
1. Запустить локальный тестовый HTTP-сервер.
2. Запустить туннель.
3. Получить публичный URL.
4. Выполнить GET на безопасный health endpoint.
5. Проверить ответ.
6. Остановить туннель.
7. Убедиться, что дочерний процесс завершён.
```

## 15. Критерии приёмки

Результат считается готовым, если:

- Созданы три независимых пользовательских скрипта.
- Каждый скрипт проверяет локальный сервер.
- Каждый скрипт обнаруживает отсутствие зависимостей.
- Установка требует согласия пользователя либо явно переданного параметра.
- ngrok корректно обрабатывает отсутствие authtoken.
- Cloudflare работает без аккаунта.
- localtunnel использует npx.
- Публичный URL определяется автоматически.
- Webhook URL формируется корректно.
- Секреты не попадают в логи.
- Скрипты корректно обрабатывают Ctrl+C.
- Все ошибки имеют понятные сообщения.
- Документация написана на русском языке.
- Примеры запуска можно копировать.
- Тесты проходят в доступном окружении.
- Ограничения тестирования явно задокументированы.

## 16. Проверка перед коммитом

Codex должен:

1. Проверить синтаксис PowerShell.
2. Проверить соответствие PowerShell 5.1 и 7.
3. Запустить доступные автоматические тесты.
4. Проверить отсутствие секретов.
5. Проверить корректность ссылок в документации.
6. Проверить Git diff.
7. Убедиться, что не изменены посторонние файлы.
8. Не добавлять исполняемые файлы туннельных клиентов в репозиторий.
9. Не коммитить временные файлы, токены и логи.
10. Создать коммит.

Сообщение коммита:

```text
feat: add automated local webhook tunnels for cloudflare ngrok and localtunnel
```

Если GitHub remote доступен, не выполнять push без отдельного разрешения.
